# 稳定性事故报告：SurfaceFlinger 看门狗崩溃导致 Android 框架重启

- **发生时间**：2026-10-13 16:46:07
- **触发场景**：设备浏览器渲染复杂页面 + 高频 `screencap` / `input swipe` 操作
- **后果**：Android 框架整体重启（软重启），**内核未重启**
- **严重性**：⚠️ **对 Kiosk 应用是关键风险，必须设计自恢复机制**

---

## 一、事故现象

测试过程中，设备所有系统服务突然不可用：

```
$ adb shell settings get global bluetooth_on
Error while accessing settings provider
java.lang.NullPointerException: Attempt to invoke interface method
'android.app.IActivityManager$ContentProviderHolder
 android.app.IActivityManager.getContentProviderExternal(...)'
 on a null object reference

$ adb shell dumpsys location
Can't find service: location
```

`settings` / `pm` / `dumpsys` 全部报 ActivityManager 为 null。

---

## 二、取证结论

### 2.1 是「软重启」，不是「重启」

| 指标 | 值 | 说明 |
|---|---|---|
| `/proc/uptime` | 12858 秒（3 h 34 min） | **内核没有重启**，持续运行 |
| `adb` 连接 | 未断开（transport_id 由 1 变 2） | adbd 存活 |
| `sys.boot_completed` | 1 | 框架已重新起来 |
| `system_server` PID | **612 → 4206** | ⚠️ **framework 重启了** |
| `surfaceflinger` PID | **133 → 3822** | ⚠️ 也重启了 |

→ 这是典型的 **Android framework soft reboot**（`SYSTEM_RESTART`），
内核、adbd 都活着，只有用户空间重启。

### 2.2 根因：SurfaceFlinger 看门狗主动 abort

Dropbox 里记录得非常清楚：

```
Drop box contents: 3 entries

2026-10-13 16:46:07 SYSTEM_RESTART (text, 257 bytes)

2026-10-13 16:46:07 SYSTEM_TOMBSTONE (compressed text, 7621 bytes)
pid: 133, tid: 368, name: SFWatchDog  >>> /system/bin/surfaceflinger <<<
signal 6 (SIGABRT), code -6 (SI_TKILL), fault addr --------
backtrace:
    #03 pc 00013ea5  /system/lib/libc.so (__libc_android_abort+36)
    #04 pc 00012524  /system/lib/libc.so (abort+4)
    #05 pc 0002cd6b  /system/lib/libsurfaceflinger.so
    #06 pc 00010a09  /system/lib/libutils.so (android::Thread::_threadLoop(void*)+112)
```

**`SFWatchDog` 是 SurfaceFlinger 自带的看门狗线程**。
它检测到合成线程长时间无响应后，**主动调用 `abort()` 自杀**（SIGABRT）。
init 随即重启 SurfaceFlinger，Android 框架因核心服务死亡而整体重启。

从 tombstone 里还能看到 `UIComposeThread` / `MMComposeThread` 存在**两代实例**
（tid 333/334 和 tid 3770/3771），说明合成线程此前已异常重建过一次。

### 2.3 崩溃前的帧率征兆

崩溃前后的 SurfaceFlinger 帧率日志（正常应 ~60 fps）：

```
16:46:28.519  fps:0.094726  dur:10556.76  max:10556.76   ← 单帧 10.5 秒
16:47:00.060  fps:0.045345  dur:22052.97  max:22052.97   ← 单帧 22 秒
16:47:07.491  fps:0.807426  dur:7431.02   max:7321.64
```

**单帧耗时飙到 10–22 秒**，远超看门狗阈值，于是被判定为挂死。

> ⚠️ **解读注意**：**空闲时**帧率低是正常的（画面没变化，SurfaceFlinger 不需要合成）。
> 上面这些数字是**在重负载期间**采集的，才代表真实卡顿。

## 三、正常负载下的真实性能（对照）

### ⚠️ 先纠正一个错误测量

早期版本写「UI 负载下 10–21 FPS」——**那是错的**。原因：测试用 `adb shell input swipe`
一条条发，每次 adb 往返约 1 秒，界面只在极稀疏的时刻需要重绘，
测到的"帧率"把大量空闲时间算进去了，是**测量方法造成的假象**。

### 正确的测法：在设备本地连续滑动

把滑动脚本推到设备上执行（避开 adb 往返开销）：

```bash
adb push swipe-load.sh /data/local/tmp/
adb shell sh /data/local/tmp/swipe-load.sh    # 设备本地连续滑 200 次
```

结果：

| 指标 | 实测值 |
|---|---|
| 帧率范围 | **43 – 56 FPS** |
| 单帧最小耗时 | **15 ms**（即 60 fps 的理论帧间隔） |
| 单帧最大卡顿 | **82 – 313 ms**（偶发） |
| 负载时 CPU | `online = 0-3`（**4 核全开**）、频率 1300 MHz |

**结论：launcher 这类常规 UI 的性能远超预期**，能跑到接近 60 fps 的水平，
偶有 82~313ms 的卡顿帧。

→ 这条修正直接影响开发建议：**不需要为了"性能差"而刻意把 UI 做得很简陋**。
（开发指南 §7 原来写的"稳定 30 fps 即可，别追求 60"过于保守，已修正。）

### 那崩溃是怎么来的？

值得注意的是：**持续滑动 200 次并没有触发崩溃**。
说明设备的常规 UI 渲染是稳的，崩溃发生在**另一类极端负载**下
（浏览器渲染复杂页面 + 高频 `screencap` + 频繁滑动叠加）。

**⚠️ 因果声明降级**：崩溃的确切触发条件**没有做单一变量隔离**，
我没有复现出"最小触发集"。目前只能说：
**在 WebView 复杂渲染 + 高频截屏的组合负载下，SurfaceFlinger 会卡死并触发看门狗。**
不要把它当成"任何重负载都会崩"。

## 四、对 Kiosk 项目的三条关键结论

### ✅ 好消息 1：框架重启后会**重新广播 `BOOT_COMPLETED`**

实测日志（框架重启后）：

```
16:46:06.888  V/ActivityManager( 4206): broadcast BOOT_COMPLETED intent
16:46:06.891  V/ActivityManager( 4206): Broadcast: Intent {
              act=android.intent.action.BOOT_COMPLETED ... } ordered=true
16:46:06.998  D/ActivityThread( 4926): BDC-Calling onReceive:
              ... cmp=com.mediatek.ppl/.PplReceiver
```

**这意味着：如果 Kiosk 应用注册了 `BOOT_COMPLETED`，框架崩溃重启后会被自动拉起。**
这是天然的容错机制——**务必注册这个广播**，哪怕你的应用已经是默认桌面。

> 前提：应用不能处于 `stopped` 状态（安装后需启动过一次）。

### ✅ 好消息 2：内核不重启，`adb` 不断线

软重启约 20–30 秒内自动恢复，`adb` 连接保持，可以远程观察和干预。
不会出现"设备彻底失联"的情况。

### ⚠️ 风险：**不要用 WebView 做持续动画界面**

这次事故的触发条件就是「WebView 复杂渲染 + 高频截屏」。
Kiosk 应用如果：

- 用 WebView 承载主界面
- 播放持续动画 / 视频
- 高频刷新图表

**就可能复现这次崩溃。**

**建议**：
- 界面用**原生 View**（避开 WebView 的老引擎和性能问题）
- 避免持续全屏动画
- 若必须用 WebView，禁止在其上叠加高频重绘

- **内核版本**：Linux **3.10.54**（2014 年前后的 LTS）

→ 进一步佐证这是一套 **ODM 在 2023 年用老 BSP 重新编译的固件**。

## 六、复现与规避

### 复现路径（谨慎，会重启框架）

```bash
# 1. 用浏览器打开一个复杂页面（如百度首页）
adb shell "am start -a android.intent.action.VIEW -d 'https://www.baidu.com'"

# 2. 高频截屏 + 滑动（放大图形栈压力）
for i in $(seq 1 30); do
  adb shell screencap -p /sdcard/x.png
  adb shell input swipe 600 640 120 640 100
done

# 3. 观察是否触发
adb shell "ps | grep system_server"   # PID 变化即已重启
adb shell "dumpsys dropbox --print" | grep -A3 SYSTEM_RESTART
```

### 规避措施

| 措施 | 说明 |
|---|---|
| 界面用原生 View | 避开 WebView 老引擎 |
| 避免持续全屏动画 | 降低合成压力 |
| 不要高频 `screencap` | 每次截屏都强制合成一帧 |
| 注册 `BOOT_COMPLETED` | 崩溃后自动恢复 |
| 应用侧加看门狗 | 主线程卡顿超时自行重启 Activity |
