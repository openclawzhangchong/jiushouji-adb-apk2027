## 一、被你抓到的问题（已修正）

### ❌ 勘误 1：「UI 帧率只有 10–21 FPS」—— **测量方法错误**

| | 内容 |
|---|---|
| 原结论 | launcher 滑动负载下 10–21 FPS，单帧卡顿最高 780 ms |
| 错误原因 | 测试用 `adb shell input swipe` **一条条发**，每次 adb 往返约 1 秒。界面只在稀疏时刻需要重绘，测到的"帧率"把大量空闲时间算进去了，是**测量假象** |
| 正确测法 | 把滑动脚本推到设备，**在设备本地连续执行**（`tools/swipe-load.sh`，200 次） |
| **实测真值** | **43 – 56 FPS**，单帧最小 **15 ms**（60fps 理论帧间隔），偶发 **82–313 ms** 卡顿帧；负载时 CPU `online=0-3`、频率 1300 MHz |
| 影响 | 开发指南里"稳定 30 fps 即可，别追求 60"**过于保守**，可能导致程序员不必要地简化界面 |

**证据**：`tools/swipe-load.sh`（可复现）

### ❌ 勘误 2：「WebView 的 `let`/`const` 都不支持」—— **测试方法错误**

| | 内容 |
|---|---|
| 原结论 | `let`/`const` 双双 FAIL |
| 错误原因 | v1 测试用 `eval('let a=1; const b=2;')`。因为 `let` 不支持导致整句抛 SyntaxError，就把 `const` 一起判成 FAIL |
| 正确测法 | 用 `new Function(src)` 做**纯语法解析测试**，绕开 eval 作用域干扰；同时把 `let` 和 `const` **分开测** |
| **实测真值** | **`const` ✅ PASS**（Chrome 从 v6 就支持）、**`let` ❌ FAIL** |
| 影响 | 结论方向没变（还是要编译到 ES5），但细节错了。已换成 v2 测试页 |

**证据**：`tools/webview-test-v2.html` + `assets/webview-v2-1/2.png`

### ❌ 勘误 3：「MAC 地址 `00:08:22:c6:a2:fb`」—— **不是稳定值**

| | 内容 |
|---|---|
| 原结论 | 设备 MAC 是 `00:08:22:c6:a2:fb`，写进了评估报告 |
| 实际情况 | 做完恢复出厂后重新采集，MAC 变成了 **`00:08:22:e6:d2:fb`** |
| 原因 | MAC 是在 `/data` 里持久化的随机值，恢复出厂后被重新生成（OUI `00:08:22` 相同但后缀完全不同） |
| 影响 | 加上序列号本来就是 MTK 占位值，**这台设备没有任何稳定的硬件唯一标识**。多设备部署时不能靠 MAC / 序列号区分设备 |

**证据**：`raw/getprop.txt`（恢复前）与本次重新采集对比

### ❌ 勘误 4：「中文输入测试失败」—— **原测试本身无效，但结论歪打正着**

| | 内容 |
|---|---|
| 原结论 | 中文输入失败 |
| 原测试的问题 | 当时点的是 (360, 200)，**根本没聚焦到任何输入框**，测试无效 |
| 重新复核 | 这次确认了：`input text '中文'` → **`Killed`**（命令进程被杀），**两次复现**。这是**命令级失败**，与焦点无关 |
| 拆成两条独立结论 | ① **`adb shell input text` 传入非 ASCII 会崩**（已验证，2/2 复现）② 设备**没有中文输入法**，仅 `LatinIME`（已验证） |

## 二、复核后获得更硬证据的结论

### ✅ `loadavg ≈ 7.8` ← 恰好 7 个 D 状态内核线程

原测试是**不同时刻**采样 loadavg 和 D 进程，只是相关性。
这次做了 3 次**同一刻**采样：

```
loadavg: 7.85 7.33 6.25   D 状态进程数: 7
loadavg: 7.78 7.32 6.25   D 状态进程数: 7
loadavg: 7.90 7.36 6.28   D 状态进程数: 7
```

7 个 D 线程（`wdtk-0~3` / `hang_detect` / `pmic_thread_kth` / `bat_thread_kthr`）+ 1 个运行中
= 8，与 loadavg 7.8~7.9 吻合。**结论成立。**

### ✅ CPU 空闲 598 MHz / 负载 1.3 GHz

原测试有一次基线读到 1300000，另一次 598000，自相矛盾。
这次连测 5 次空闲状态，**5/5 都是 598000**。
之前那次 1300000 是**测试脚本自身刚启动的活动**造成的瞬态——解释了矛盾。

### ✅ **TLS 1.3 不可用 —— 从「推断」升级为「实测」**

原来写「TLS 1.3 需要 Android 10+，这台不支持」是**推断**，没有实测。
这次做了对照实验（本机两个 HTTPS 服务分别锁死 TLS 版本）：

| 服务端配置 | 设备表现 | 结论 |
|---|---|---|
| 仅 TLS 1.2（对照） | 弹自签证书警告，**握手成功** | ✅ |
| 仅 TLS 1.3（实验） | 「**无法建立安全连接**」 | ❌ |

截图：`assets/tls12-device.png` / `assets/tls13-device.png`

**顺带**：TLS 1.2 可用也是靠这个对照组才真正验证的。

### ✅ SurfaceFlinger 看门狗崩溃

直接 tombstone 证据，本来就是最硬的一条，复核无变化。

### ✅ 新增发现：`crypto.subtle` 可用

v2 测试页补测了这一项，**PASS**。WebCrypto 可用，原来没测到。

## 三、复核后「因果声明降级」的结论

### ⚠️ 崩溃触发条件：从「确定」降为「未隔离」

原报告把崩溃归因于「浏览器渲染复杂页面 + 高频 screencap + 频繁滑动叠加」，
听起来很确定。实际上：

- **没有做单一变量隔离实验**
- **持续滑动 200 次没有触发崩溃**（说明常规 UI 渲染是稳的）

**修正后的表述**：只能说「在 WebView 复杂渲染 + 高频截屏的组合负载下，SurfaceFlinger 会卡死并触发看门狗」。
**不要**把它理解成「任何重负载都会崩」——我没有复现出最小触发集。

## 五、这次复核的方法论收获

1. **adb 往返会污染性能测量**。任何"帧率/延迟/speedup"类指标，
   必须把负载脚本推到设备本地跑，不能逐条 `adb shell` 发。
2. **eval 测试语法支持不可靠**。测引擎语法能力要用 `new Function()`，
   且要把每个特性**单独**测——否则一个失败会连坐后面的。
3. **摘录式采集（getprop）要标注采集时刻**。这次 MAC 变化就是因为
   只在开头采了一次，后面设备状态变了没人发现。
4. **"没测"和"测了不支持"是两回事**。TLS 1.3 那条原本就是"按公开知识推断"，
   应该一开始就标注成推断而不是结论。
